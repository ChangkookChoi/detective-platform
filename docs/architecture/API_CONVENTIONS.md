# API 규칙

## 1. 적용 범위

Next.js Route Handler, Server Action, 수집기와 웹 사이의 데이터 계약에 적용한다. 내부 UI 전용 로직은 불필요하게 공개 HTTP API로 만들지 않는다.

## 2. 기본 원칙

- Route Handler는 얇게 유지하고 유스케이스는 도메인/애플리케이션 모듈에 둔다.
- 모든 외부 입력은 스키마로 검증한다.
- 공개 API는 승인·공개 상태 데이터만 반환한다.
- 관리자 쓰기와 수집기 적재는 인증, 권한, 감사 요건을 각각 적용한다.
- 사건 내용, 조사 대상자 정보, 통화 내용과 녹취를 받는 필드를 만들지 않는다.
- 새 공개 계약이나 호환성 파괴 변경은 문서와 테스트를 함께 갱신한다.

## 3. URL과 버전

- 리소스는 복수형 명사를 사용한다: `/api/offices`, `/api/admin/review-items`.
- 공개 식별자는 안정적인 slug 또는 opaque ID를 사용한다.
- 필터는 검색 파라미터로 표현한다: `?region=seoul-gangnam&category=family`.
- `region`은 검수된 사무소 소재지 slug이며 서비스 가능 지역을 의미하지 않는다. 상위 지역을 지정하면 활성 하위 지역에 속한 업체를 포함한다.
- `category`는 활성 업무 분야 slug만 허용한다. 여러 값을 지원할지는 실제 UI 요구가 생길 때 계약으로 추가한다.
- 초기 내부 API는 별도 버전 없이 운용할 수 있다. 외부 소비자가 생기거나 호환성 유지가 필요해지면 `/api/v1`을 도입한다.
- 관리자와 내부 수집 경로는 공개 경로와 명확히 분리한다.

## 4. HTTP 의미

- `GET`: 조회, 안전하고 멱등
- `POST`: 생성 또는 이벤트 기록
- `PATCH`: 일부 필드 변경 또는 상태 전환
- `DELETE`: 실제 삭제가 정책상 허용될 때만 사용; 보통 상태 전환 우선

적절한 상태 코드를 사용한다: `200`, `201`, `204`, `400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`. 존재 여부 자체가 민감한 관리자 리소스는 권한 정책에 맞춰 응답한다.

## 5. 응답 형식

단건 예시:

```json
{
  "data": {
    "id": "opaque-id",
    "slug": "example-office",
    "name": "예시 탐정사무소",
    "lastVerifiedAt": "2026-07-22T00:00:00Z"
  }
}
```

목록 응답은 `data` 배열과 `pageInfo`를 사용한다. 소규모 초기 목록은 페이지 번호 방식도 가능하지만 정렬 기준을 고정하고 최대 `limit`을 제한한다.

오류 예시:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "요청 값을 확인해 주세요.",
    "requestId": "opaque-request-id",
    "details": [
      { "field": "region", "reason": "unsupported_value" }
    ]
  }
}
```

운영 환경 오류에는 스택, SQL, 비밀값, 내부 경로를 포함하지 않는다.

## 6. 필드 규칙

- JSON 필드는 `camelCase`, 시각은 ISO 8601 UTC 문자열을 사용한다.
- 금액이 추가될 경우 부동소수점 대신 최소 화폐 단위 정수를 사용한다.
- `null`, 누락, 빈 문자열의 의미를 계약별로 명확히 한다.
- enum 값은 안정적인 영문 소문자 식별자를 사용한다.
- 전화번호는 공개 응답에서 승인된 표시값만 반환하고 분석 이벤트 응답에는 포함하지 않는다.
- 공개 업체 응답은 MVP에서 대표 전화번호와 소재 지역을 각각 하나만 반환한다.
- 업무 분야는 관리형 객체 배열로 반환하며 수집된 자유 문자열을 그대로 노출하지 않는다.

## 7. 페이지네이션·필터·정렬

- 허용된 필터와 정렬 키를 allowlist로 제한한다.
- 존재하지 않거나 비활성인 지역·업무 분야 slug는 잘못된 필터로 처리한다. 서버 렌더링 페이지의 404 여부와 API의 `400` 응답은 라우트 계약별로 일관되게 정한다.
- 기본 정렬은 결정적이어야 한다. 광고 노출은 일반 정렬과 구분하여 표시한다.
- 임의 SQL 조각이나 클라이언트 제공 컬럼명을 그대로 사용하지 않는다.
- 검색 결과가 없어도 `200`과 빈 배열을 반환한다.

## 8. 인증, CSRF, 속도 제한

- 공개 읽기와 최소 분석 이벤트 외의 쓰기는 인증한다.
- 관리자 권한은 서버에서 매 요청 확인한다.
- 쿠키 기반 쓰기는 CSRF 방어와 Origin 검사를 적용한다.
- 로그인, 관리자 쓰기, 정정 요청, 이벤트 수집에는 목적에 맞는 속도 제한을 둔다.
- 수집기 인증정보는 회전 가능하고 최소 권한이어야 한다.

## 9. 멱등성과 동시성

- 재시도 가능한 수집 적재와 중요한 관리자 작업은 idempotency key 또는 자연 고유키를 사용한다.
- 승인 시 후보 버전이나 `updatedAt`을 검사하여 뒤늦은 승인이 최신 운영값을 덮어쓰지 않게 한다.
- 충돌은 `409 CONFLICT`로 알리고 사용자가 최신 상태를 다시 확인하게 한다.

## 10. 캐시와 관측성

- 공개 GET만 명시적 캐시 대상이며 관리자·검수 응답은 비공개 캐시 정책을 사용한다.
- 승인 또는 비공개 전환 후 관련 목록·상세 캐시를 무효화한다.
- 응답과 로그를 연결할 요청 ID를 사용하되 개인정보를 식별자로 삼지 않는다.
- 메트릭은 지연, 오류율, 상태 코드, 작업 결과 중심으로 수집한다.

## 11. 공개 분석 이벤트

- `POST /api/analytics/events`는 `officeId`, `type`, `sessionId`만 받는다.
- 공개 이벤트 type은 `office_detail_view`, `phone_click`으로 제한한다.
- 같은 출처의 `application/json` 요청과 공개 상태 업체만 허용한다.
- 성공과 중복은 본문 없는 `204`, 잘못된 입력은 `400`, 다른 출처는 `403`, 비공개·없는 업체는 `404`, 세션별 제한 초과는 `429`로 응답한다.
- 응답에는 전화번호, 중복 키, 세션 식별자나 집계값을 포함하지 않는다.
