# 사용자 흐름

## 공통 원칙

- 사용자는 회원가입 없이 공개 정보를 탐색한다.
- 사건 내용이나 조사 대상자 정보를 입력받지 않는다.
- 공개 화면에는 승인된 운영값만 사용한다.
- 광고는 일반 결과와 구분하며 품질 추천이나 순위로 표현하지 않는다.

## 흐름 1: 지역과 업무 분야로 업체 찾기

1. 사용자가 홈 또는 업체 목록에 진입한다.
2. 지역과 업무 분야를 선택한다.
3. 시스템은 공개 상태인 업체만 필터링하여 보여준다.
4. 사용자는 업체명, 지역, 업무 분야, 확인일을 비교한다.
5. 사용자가 업체를 선택하면 상세 페이지로 이동한다.
6. 결과가 없으면 조건 완화 방법을 안내하며 임의의 추천 결과를 끼워 넣지 않는다.

성공 조건: 사용자가 사건 내용을 제출하지 않고 관련 업체 상세에 도달한다.

## 흐름 2: 업체 정보 확인 후 전화 연결

1. 사용자가 업체 상세에서 주소, 업무 분야, 소개, 출처, 최종 확인일을 확인한다.
2. 사용자가 전화 연결 버튼을 누른다.
3. 시스템은 개인정보를 포함하지 않는 클릭 이벤트를 기록한다.
4. 지원 기기에서는 `tel:` 링크를 통해 전화 앱으로 넘긴다.
5. 플랫폼 과금 없음과 통신사 요금 가능성을 안내한다.

성공 조건: 전화 연결 동작이 실행된다. 클릭은 통화 성립이나 계약 성사를 뜻하지 않는다.

## 흐름 3: 정보 오류 또는 정정 요청

1. 사용자가 상세 페이지의 정보 수정 요청 경로를 선택한다.
2. 시스템은 업체명, 대표 전화번호, 주소, 소개 중 한 항목과 제안 공개값, 요청자 관계, 선택적 공개 근거 URL만 요청한다.
3. 요청자 연락처는 받지 않으며 사건·상담 내용과 조사 대상자 등 개인의 정보를 입력하지 않았다는 확인을 요구한다.
4. 시스템은 공개 상태 업체를 다시 확인하고 같은 업체의 24시간 내 동일 요청과 과다 요청을 차단한 뒤 `correction_request` 검수 후보를 만든다.
5. 운영자는 요청자 관계 표기가 권한 증명이 아님을 전제로 권한 또는 근거와 기존 공개 출처를 별도로 확인한다.
6. 요청자가 제안한 URL을 자동으로 신뢰하지 않고 운영자가 직접 확인한 공개 출처와 유형을 입력해 일반 검수 절차를 진행한다.
7. 승인된 필드만 운영값에 반영하고 확인 출처, 필드 근거, 최종 확인일과 감사 이력을 같은 트랜잭션에서 갱신한다.

성공 조건: 요청 내용, 근거, 처리자, 처리 결과가 감사 가능하게 남고 미검증 변경은 공개되지 않는다.

## 흐름 4: 자동 수집 후보 검수

1. 수집기가 출처 정책을 확인하고 허용된 페이지에서 최소 필드를 수집한다.
2. 원본 참조, 수집 시각, 정규화 값과 추출기 버전을 저장한다.
3. 현재 운영값과 비교해 신규 또는 변경 후보를 만든다.
4. 관리자가 원문, 수집값, 현재 운영값을 비교한다.
5. 신규 후보는 공개 URL slug, 검수된 최하위 소재 지역, 관리형 업무 분야와 대표 출처 유형을 지정한다.
6. 관리자는 제안값 승인, 허용된 후보 필드의 수정 후 승인, 보류 또는 반려를 선택하고 사유를 기록한다.
7. 승인 트랜잭션에서 신규 업체 또는 기존 운영값, 대표 출처, 필드 근거, 공개 상태와 감사 이력을 함께 갱신한다.

예외:

- 요청 실패: 제한된 재시도 후 실패를 기록하고 기존 운영값은 유지한다.
- 출처에서 사라짐: 자동 삭제하지 않고 폐업/삭제 의심 후보로 보낸다.
- 전화·주소·상호 변경: 다른 필드보다 우선하여 명시적으로 검수한다.
- 동시 수정: 검수 항목과 기존 업체의 변경 시각이 화면 조회 시점과 다르면 승인하지 않고 최신 내용을 다시 확인한다.
- 신규 필수 정보 부족: 업체를 일부만 만들지 않고 전체 승인을 롤백하여 검수 대기 상태를 유지한다.
- 정정 요청 근거 부족: 제안 URL만으로 승인하지 않고 보류 또는 반려하며, 운영자가 확인한 안전한 HTTP(S) 공개 출처가 없으면 승인하지 않는다.

## 흐름 5: 공식 출처 수동 후보 등록

1. 인증된 운영자가 자동 추출이 어려운 업체의 공식 공개 페이지를 직접
   확인한다.
2. 운영자는 공식 출처 URL, 업체명, 사업상 공개 대표 전화와 소재지 주소만
   입력한다.
3. 운영자는 운영 주체가 직접 관리하는 출처와 정확한 한 개 사무소의 정보임을
   확인하고 사건·상담·조사 대상자·개인 연락처 등 민감정보를 입력하지
   않았음을 확인한다.
4. 시스템은 두 필수 확인, URL과 필드 형식을 서버에서 검증하고 같은 출처
   URL·주소의 `pending` 또는 `on_hold` 신규 후보가 있는지 확인한다.
5. 제출자 Clerk 사용자 ID, 원본 참조와 정규화 값을 고위험 `new_office`
   검수 후보로 저장한다. 이 단계에서는 운영 업체를 만들지 않는다.
6. 운영자는 일반 신규 후보와 동일하게 원문, 지역과 관리형 업무 분야를 다시
   확인한 뒤 승인·수정 후 승인·보류·반려한다.

성공 조건: 자동 파서 없이도 출처와 제출자를 추적할 수 있는 비공개 후보가
생기고, 별도 승인 전 공개 데이터는 변하지 않는다.

예외:

- 같은 공식 출처 URL과 주소의 미처리 후보가 있음: 중복 등록하지 않고 기존
  후보를 확인하도록 안내한다.
- 하나의 공식 페이지에 주소가 다른 복수 지점이 명확히 구분됨: 사무소별
  최소 사실 필드를 각각 확인해 별도 후보로 등록한다.
- 공식 출처 또는 필수 사실 필드가 불명확함: 등록하지 않고 출처 등록부에서
  보류한다.
- 공식성 또는 민감정보 미포함 필수 확인 누락: 브라우저의 `required`
  검사와 무관하게 서버 도메인 규칙으로 등록을 거부한다.
- 소개 문구·이미지·사건·상담 내용·조사 대상자 정보·개인 연락처: 수동 입력
  범위에 포함하지 않는다.

## 흐름 6: 사전검증 후보 일괄 등록·승인

1. 운영자는 구조화 manifest와 24시간 이내 사전검증 결과를 관리자 일괄 검수
   화면에 함께 제출한다.
2. 시스템은 두 파일의 배치 ID·검증일·후보 URL을 대조하고 모든 후보가 통과한
   경우에만 비공개 검수 후보를 일괄 생성한다.
3. 기존 미처리 동일 후보는 재사용하고 정확히 같은 공개 업체는 건너뛰며,
   값이 다른 중복은 자동 승인하지 않는다.
4. 시스템은 manifest의 slug·최하위 소재 지역·업무 분야·출처 유형과 근거
   메모를 후보에 보존해 관리자 표에 표시한다.
5. 운영자는 공식 원문과 행별 값을 대조하고 정상 건만 선택한 뒤 일괄 승인
   확인과 사유를 한 번 제출한다.
6. 시스템은 선택 업체마다 기존 승인 트랜잭션을 실행해 독립된 업체·출처·
   필드 근거·감사 이력을 만든다. 충돌한 건은 미처리로 남기고 정상 건은 계속
   처리한다.
7. 배치 실행은 공개 상세와 DB 무결성을 일괄 검증한다.

성공 조건: 업체별 반복 입력·페이지 전환 없이도 사람의 명시적 행별 검수와
승인 경계를 지키며 여러 업체를 공개한다.

## 흐름 7: 광고 또는 강화 상품 노출

1. 운영자가 계약 범위와 노출 기간을 확인한다.
2. 광고 대상도 기본 업체 검수를 통과했는지 확인한다.
3. 시스템은 광고임을 명확히 표시하여 노출한다.
4. 광고 노출·클릭은 일반 탐색 지표와 분리 집계한다.
5. 기간 종료 또는 계약 해지 시 광고 노출만 종료하고 기본 정보는 공개 정책에 따라 유지한다.

성공 조건: 사용자가 유료 노출을 식별할 수 있고 광고 여부가 품질 보증이나 일반 순위로 오인되지 않는다.
