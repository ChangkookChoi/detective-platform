# 보안 정책

## 1. 보안 목표

- 승인되지 않은 업체 정보의 공개와 관리자 기능 접근을 막는다.
- 공개 사업 정보와 운영 데이터를 정확하고 추적 가능하게 유지한다.
- 사건 내용, 조사 대상자 정보, 통화 내용처럼 서비스가 필요로 하지 않는 민감정보를 수집하지 않는다.
- 비밀값, 개인정보, 내부 오류 정보가 코드·로그·응답으로 유출되지 않게 한다.

## 2. 데이터 최소화

- 사건 접수용 자유 입력란을 제공하지 않는다.
- 정정 요청은 업체 정보 확인에 필요한 최소 항목만 받으며 민감 내용 입력 금지를 안내한다.
- 통화 연결 성공 여부, 통화 내용, 녹취를 수집하지 않는다.
- 분석은 목적에 필요한 최소 이벤트로 제한하고 원시 IP·User-Agent의 장기 보존을 피한다.
- 공개 분석은 원시 IP·User-Agent를 수집하지 않고 탭 세션 UUID를 서버에서 해시하며, 중복 방지 행은 48시간 뒤 제거하고 일별 업체 합계만 영속 보관한다.
- 실제 개인정보나 운영 비밀을 테스트·시드 데이터로 쓰지 않는다.

## 3. 인증과 권한

- 관리자 경로와 모든 관리자 쓰기는 인증을 요구한다.
- 관리자 신원과 세션은 [ADR-0005](../decisions/ADR-0005-clerk-admin-auth.md)에 따라 Clerk로 관리하고 자체 비밀번호나 JWT를 구현하지 않는다.
- MVP의 `reviewer`, `admin` 역할은 서버 전용 Clerk 사용자 ID allowlist로 부여하며 `admin`은 검수 권한을 포함한다.
- 역할별 최소 권한을 적용하고 승인, 광고 관리, 정책 변경 권한을 구분할 수 있게 설계한다.
- 서버에서 매 요청 권한을 확인하며 UI 숨김만으로 보호하지 않는다.
- 중요 변경은 처리자, 대상, 시각, 사유를 감사 로그에 남긴다.
- 수집기 자격 증명은 후보 적재에 필요한 DB/API 권한으로 제한한다.

## 4. 애플리케이션 보안

- TypeScript strict mode와 런타임 스키마 검증을 함께 사용한다.
- SQL은 파라미터화하고 허용된 필터·정렬 값만 받는다.
- 출력 문맥에 맞는 escaping을 적용하고 임의 HTML 렌더링을 피한다.
- 쿠키는 `Secure`, `HttpOnly`, 적절한 `SameSite` 설정을 사용한다.
- 상태 변경 요청에 CSRF 방어와 Origin 검사를 적용한다.
- 로그인, 정정 요청, 관리자 쓰기, 이벤트 수집에 속도 제한과 오남용 방어를 둔다.
- 보안 헤더(CSP, HSTS, frame 제한, MIME sniffing 방지 등)는 배포 환경에 맞게 검증한다.

## 5. 비밀과 환경변수

- 비밀키, 토큰, 실제 자격 증명을 Git에 커밋하지 않는다.
- 필요한 환경변수 이름과 용도만 `.env.example`에 기록한다.
- 개발·미리보기·운영 환경 자격 증명을 분리하고 정기 또는 사고 시 회전한다.
- 로그, 에러 응답, 빌드 산출물, 클라이언트 번들에 서버 비밀을 포함하지 않는다.

## 6. 수집기와 외부 요청

- 허용된 프로토콜과 호스트를 관리하여 SSRF 위험을 줄인다.
- redirect 횟수, 응답 크기, timeout을 제한한다.
- 내려받은 콘텐츠를 신뢰하지 않고 파싱하며 실행하지 않는다.
- 사이트 접근 통제를 우회하지 않는다.
- 외부 응답의 민감하거나 과도한 원문을 로그에 남기지 않는다.

## 7. 데이터베이스와 백업

- 애플리케이션, 관리자 작업, 수집기에 최소 권한 계정을 사용한다.
- 네트워크 접근을 제한하고 전송 구간 암호화를 사용한다.
- migration은 검토 가능하고 되돌림 또는 복구 계획을 가져야 한다.
- 백업을 암호화하고 접근·보존 기간을 제한하며 복구를 정기 검증한다.
- 운영 데이터의 수동 변경을 최소화하고 불가피한 경우 기록한다.

## 8. 로깅과 모니터링

- 인증 실패, 권한 거부, 비정상적인 관리자 변경, 대량 수집 실패를 모니터링한다.
- 로그에는 요청 ID·작업 ID와 비민감 상태만 남긴다.
- 전화번호 전체, 사건 내용, 토큰, 쿠키, 환경변수 값, SQL 파라미터를 기록하지 않는다.
- 관리자 감사 로그와 일반 애플리케이션 로그의 접근 권한과 보존 목적을 구분한다.

## 9. 취약점과 의존성

- 잠금 파일을 유지하고 의존성 변경을 리뷰한다.
- 정기적으로 lint, build, 테스트, 의존성 취약점 점검을 실행한다.
- `npm audit fix --force`처럼 호환성을 깨뜨릴 수 있는 자동 수정은 명시적 검토 없이 실행하지 않는다.
- 심각도, 악용 가능성, 노출 범위를 기준으로 패치 우선순위를 정한다.

## 10. 사고 대응

1. 발견 내용을 기록하고 담당자에게 알린다.
2. 영향을 받는 기능·계정·데이터를 식별하고 추가 피해를 차단한다.
3. 유출 가능성이 있는 비밀을 회전하고 증거를 보존한다.
4. 법적 통지와 사용자 안내 필요성을 평가한다.
5. 안전한 수정과 복구를 검증한다.
6. 원인, 영향, 타임라인, 재발 방지를 문서화한다.

보안 문제 신고 채널과 대응 담당은 공개 출시 전에 확정한다.
