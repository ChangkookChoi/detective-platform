# 데이터 검증 정책

## 1. 목적

자동 수집 또는 수동 제보로 들어온 업체 정보가 사람의 확인 없이 공개되지 않도록 하고, 공개 정보의 근거와 최신성을 추적 가능하게 유지한다.

## 2. 역할

- 수집기: 후보 생성과 변경 감지. 승인 권한 없음.
- 검수자: 출처 비교, 값 수정, 승인·보류·반려.
- 관리자: 정책 예외, 분쟁, 폐업·비공개, 대량 변경 판단.

고위험 변경이나 이해관계가 있는 검수는 가능하면 다른 담당자의 재확인을 받는다.

## 3. 공개 전 필수 확인

- 업체명과 동일 업체 여부
- 사업상 공개된 전화번호인지와 전화 형식
- 주소 및 대표 지역 분류
- 업무 분야가 출처로 뒷받침되는지
- 출처 URL 접근 가능 여부와 확인 시각
- 과장, 불법 가능성, 보증으로 오인될 표현 여부
- 중복 업체 여부

공개 상태로 전환하려면 최소 한 개의 신뢰 가능한 출처와 최종 확인일이 있어야 한다.

MVP에서 업체 한 건은 하나의 실제 사무소 또는 지점이다. 동일 브랜드라도 주소나 대표 연락처가 다르면 별도 항목으로 검수한다. 반대로 상호 표기만 다르고 주소·전화번호·공식 출처가 같은 경우에는 중복 후보로 보고 병합 여부를 확인한다.

지역 분류는 검수된 소재지 주소를 기준으로 하며 업체가 홍보하는 출장·서비스 가능 지역을 소재 지역으로 등록하지 않는다. 업무 분야는 출처의 자유 문구를 관리형 분류에 매핑하고, 불명확하거나 여러 의미로 해석되는 경우 보류한다.

## 4. 출처 우선순위

일반적으로 공식 업체 채널과 신뢰 가능한 공공 자료를 우선하되, 출처의 목적과 최신성을 함께 본다. 제3자 디렉터리 하나만으로 중요 필드 변경을 확정하지 않는다. 출처끼리 충돌하면 공개값을 유지하거나 보류하고 추가 근거를 찾는다.

이름, 대표 전화번호, 주소와 각 업무 분야는 어떤 출처가 해당 값을 뒷받침했는지 필드별 근거를 기록한다. 업체 전체에 출처가 연결되어 있다는 사실만으로 모든 필드를 검증한 것으로 간주하지 않는다.

## 5. 검수 결과

- `approved`: 제안값을 그대로 승인
- `approved_with_edits`: 근거에 맞게 수정 후 승인
- `on_hold`: 근거 부족, 충돌, 법적·정책 검토 필요
- `rejected`: 잘못된 매칭, 품질 부족, 정책 위반

결정, 사유, 처리자, 처리 시각, 참조 출처를 기록한다. 승인과 운영값 갱신은 원자적으로 처리한다.

신규 수집 후보를 승인할 때는 제안된 업체 필드 외에 고유 slug, 검수된 최하위 소재 지역, 최소 한 개의 활성 업무 분야와 대표 출처 유형을 지정한다. 업체, 업무 분야 연결, 대표 출처, 필드별 근거, 검수 항목의 업체 연결, 감사 이력과 공개 상태는 한 트랜잭션에서 생성한다. 하나라도 공개 조건을 충족하지 못하면 부분 업체를 남기지 않는다.

기존 업체의 변경 후보는 후보가 제안한 필드만 수정할 수 있으며 다른 운영 필드는 화면 입력값으로 덮어쓰지 않는다. `approved`는 DB에 저장된 제안값을 사용하고, `approved_with_edits`는 검수자가 입력한 허용 필드와 최종 적용 스냅샷을 감사 이력에 남긴다. 두 방식 모두 수집 출처를 DB에서 다시 확인하고 검수 항목과 업체의 동시 변경 여부를 검사한다.

`suspended`, `closed_suspected`, `archived` 업체는 일반 신규·필드 변경 승인으로 공개 상태를 복구하지 않는다. 중지 사유 해소, 폐업 여부와 복구 근거를 확인하는 별도 상태 관리 절차를 거친다.

## 6. 변경 위험도

### 높음

상호, 전화번호, 주소, 공개/폐업 상태, 업체 동일성 변경이다. 항상 명시적 검수하며 필요하면 복수 출처 또는 직접 확인을 요구한다.

### 중간

업무 분야, 소개, 영업 관련 정보처럼 사용자의 선택에 영향을 주는 변경이다. 출처 문맥과 홍보성 표현을 확인한다.

### 낮음

표기 통일, 오탈자, 비의미적 공백 등이다. 자동 정규화할 수 있으나 원본과 규칙 버전을 추적한다. 낮은 위험도라도 자동 공개는 별도 정책 승인 전 허용하지 않는다.

## 7. 재검증

- 모든 공개 업체에 `last_verified_at`을 유지한다.
- 재검증 주기는 출처 안정성, 변경 위험, 이용량에 따라 정하되 출시 전 구체적 SLA를 확정한다.
- 확인 기한이 지난 정보는 관리자 대기열에 표시한다.
- 출처 접근 실패만으로 확인일을 갱신하지 않는다.
- 전화 연결 실패 신고, 반복 정정 요청, 출처 불일치는 우선 재검증 신호다.

## 8. 폐업·삭제 의심

404, 검색 결과 미노출, 전화 불통 하나만으로 폐업을 확정하지 않는다. `closed_suspected` 후보로 만들고 추가 출처 또는 업체 확인을 거친다. `closed_suspected` 업체는 공개하지 않는다. 사용자 피해 위험이 높으면 `suspended`로 임시 비공개할 수 있으며 사유와 복구 조건을 기록한다. 폐업이나 중복이 확정되면 `archived`로 전환하고 기존 slug는 재사용하지 않는다.

## 9. 지역·업무 분야 기준 데이터

- 지역은 서울·경기 행정구역 계층과 실제 주소가 일치하는지 확인한다.
- 경기 지역은 시·군·구 깊이가 다를 수 있으므로 이름만 보고 임의의 고정 단계에 매핑하지 않는다.
- 초기 업무 분야는 데이터 모델에 정의된 다섯 가지 관리형 분류만 사용한다.
- 하나의 출처 문구를 여러 업무 분야로 확대 해석하지 않는다.
- 비활성 지역이나 업무 분야는 신규 업체에 연결하지 않고, 기존 연결은 운영자가 대체 분류 또는 공개 유지 여부를 결정할 때까지 보존한다.

## 10. 광고 데이터

광고 또는 강화 상품 여부와 관계없이 기본 업체 정보에는 같은 검수 기준을 적용한다. 광고 계약이 정보 정확성의 근거가 되지 않으며 계약 종료가 기본 업체 정보 자동 삭제의 근거도 아니다.

## 11. 감사와 품질 관리

- 승인 누락 공개 건수를 0으로 유지한다.
- 표본 재검수로 검수자 간 일관성과 오류율을 확인한다.
- 대량 승인·반려는 사유와 대상 범위를 별도 기록한다.
- 감사 이력은 권한 있는 사용자만 조회하며 일반 수정 기능으로 변경하지 않는다.
