# ADR-0003: 기본 데이터베이스로 PostgreSQL 사용

- 상태: 승인
- 결정일: 2026-07-22

## 맥락

업체, 지역, 업무 분야, 출처, 수집 후보, 검수 이력과 광고 배치는 명확한 관계와 무결성 제약을 가진다. 승인과 공개값 변경은 원자적으로 처리되어야 하며, 초기 약 100개 업체 검색에는 별도 검색 엔진이 필요하지 않다.

## 결정

웹과 수집기의 기본 영속 저장소로 PostgreSQL을 사용한다.

- 관계, 고유 제약, 외래키와 트랜잭션으로 데이터 무결성을 보장한다.
- 수집값과 승인된 운영값을 논리적으로 분리한다.
- 초기 지역·업무 분야 검색과 정렬은 PostgreSQL 인덱스로 처리한다.
- 스키마 변경은 migration으로 관리한다.
- 애플리케이션과 수집기는 역할별 최소 권한 계정을 사용한다.
- Elasticsearch/OpenSearch는 초기 범위에 포함하지 않는다.

ORM, query builder, migration 도구, 호스팅 공급자는 구현 시 별도로 비교하며 이 ADR에서 고정하지 않는다.

## 결과

장점:

- 검수 승인과 운영값 갱신을 하나의 트랜잭션으로 처리할 수 있다.
- 관계형 모델과 제약으로 중복·고아 데이터를 줄인다.
- JSON, 텍스트 검색, 집계 등 초기 요구를 한 저장소에서 해결할 수 있다.
- 운영 경험과 도구 생태계가 넓다.

단점:

- 웹과 수집기가 공유 스키마 변경을 조율해야 한다.
- 대규모 전문 검색이나 분석 요구에는 별도 시스템이 필요할 수 있다.
- 백업, connection 관리, migration 운영 역량이 필요하다.

## 대안

- SQLite: 로컬 단순성은 높지만 동시 운영, 관리형 배포, 권한과 확장 요구에 불리하다.
- 문서형 데이터베이스: 유연하지만 현재 도메인의 관계와 승인 트랜잭션에 이점이 작다.
- PostgreSQL + Elasticsearch/OpenSearch: 검색 기능은 강력하지만 현재 데이터 규모와 필터 요구에는 운영 비용이 과도하다.

## 재검토 조건

측정된 검색 품질·지연이 PostgreSQL 최적화로 충족되지 않거나, 분석 워크로드가 운영 트랜잭션에 지속적으로 영향을 줄 때 읽기 모델 또는 별도 검색·분석 저장소를 검토한다.
