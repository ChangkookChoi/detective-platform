# ADR-0006: 개인정보 최소화 일별 분석 집계

- 상태: 승인
- 결정일: 2026-07-22

## 맥락

MVP는 업체 상세 조회와 전화 버튼 클릭을 업체별·일별로 파악해야 한다. 이 지표는 탐색 수요를 학습하기 위한 내부 운영값이며 통화 성립, 계약 성사, 업체 품질이나 공개 순위를 뜻하지 않는다.

중복 요청과 단순 봇 트래픽을 그대로 세면 지표가 왜곡되지만, 이를 막기 위해 원시 IP, User-Agent, 전화번호나 장기 브라우저 식별자를 저장하는 것은 제품의 개인정보 최소화 원칙과 맞지 않는다. 초기 트래픽 규모에서는 개별 이벤트를 장기 보존할 이유도 작다.

## 결정

PostgreSQL에 업체별·한국 시각 기준 일별 집계를 영속 저장한다.

- 현재 집계 대상은 `office_detail_view`와 `phone_click`만 허용한다.
- 브라우저는 탭 세션 동안만 유지하는 임의 UUID를 생성한다.
- 서버는 세션 UUID 원문을 저장하지 않고 SHA-256 해시를 포함한 중복 방지 키만 저장한다.
- 같은 탭 세션·업체·이벤트는 같은 한국 날짜에 한 번만 집계한다.
- 중복 방지용 원시 이벤트는 48시간만 유지하며 이벤트 기록 시 만료 행을 정리한다.
- 일별 집계에는 업체, 한국 날짜와 이벤트별 정수 합계만 저장한다.
- 한 탭 세션은 한국 날짜 기준 최대 50개의 서로 다른 이벤트만 기록할 수 있다.
- 이벤트 API는 같은 출처의 JSON `POST`만 받고 공개 상태 업체에 대해서만 기록한다.
- 원시 IP, User-Agent, Referrer, 전화번호, 검색 쿼리, 통화 성립 여부와 사건 관련 정보는 저장하지 않는다.
- 이벤트 기록 실패는 공개 상세 렌더링이나 `tel:` 이동을 막지 않는다.
- 집계는 내부 제품 지표로만 사용하고 업체 품질, 추천 또는 공개 순위에 사용하지 않는다.

광고 이벤트는 기존 enum에 예약되어 있지만 광고 노출 계약과 표시가 구현되기 전에는 공개 이벤트 API에서 허용하지 않는다.

## 결과

장점:

- 장기 데이터에는 브라우저나 네트워크 식별자 없이 업체별 일별 합계만 남는다.
- 개발 모드 중복 실행, 새로고침과 단순 재시도로 인한 중복을 줄인다.
- 별도 분석 공급자 없이 현재 PostgreSQL과 모듈형 모놀리스 안에서 MVP 지표를 검증한다.
- 전화 이동은 분석 API 장애와 분리된다.

단점:

- 탭을 새로 열거나 세션 UUID를 바꾸는 트래픽은 별도 방문으로 집계될 수 있다.
- 같은 탭에서 하루에 여러 번 발생한 실제 전화 클릭은 한 번으로 집계되어 원시 클릭 수보다 보수적이다.
- IP 기반 방어를 사용하지 않으므로 정교한 봇이나 의도적인 지표 조작을 완전히 막지 못한다.
- 중복 방지 행 정리는 이벤트 요청이 들어올 때 수행되므로 트래픽이 완전히 없으면 정리가 다음 요청까지 지연된다.

## 대안

- 원시 이벤트 장기 보존: 상세 분석은 쉽지만 식별자 보존과 삭제 운영 부담이 커서 채택하지 않았다.
- IP 또는 User-Agent 해시: 속도 제한은 강해지지만 가명 식별자 처리와 개인정보 위험이 커서 채택하지 않았다.
- 외부 분석 서비스: 대시보드와 봇 필터 기능은 강하지만 제3자 전송, 동의와 비용 검토가 선행되어야 하므로 도입하지 않았다.
- 일별 합계만 저장하고 중복 방지를 하지 않음: 가장 단순하지만 새로고침과 개발 중복 실행에 취약해 완료 정의를 충족하지 못한다.

## 재검토 조건

실제 트래픽에서 봇 비율이나 집계 오차가 의사결정을 방해하거나, 광고 성과 측정·유입 경로·다중 기기 분석이 필요해지거나, 개인정보·쿠키 관련 법무 검토 결과가 현재 방식과 맞지 않을 때 동의 관리, 서버 측 봇 방어, 집계 저장소 또는 외부 분석 서비스를 별도 ADR로 비교한다.
