# ADR-0005: 관리자 인증에 Clerk 사용

- 상태: 승인
- 결정일: 2026-07-22

## 맥락

MVP 운영자는 신규 업체와 변경 후보를 검수하고 공개 상태를 변경한다. 관리자 경로와 모든 쓰기는 신원 확인, 최소 권한, 서버 측 재검사와 감사 가능한 처리자 식별자가 필요하다. 직접 비밀번호, 세션 쿠키 또는 JWT를 구현하면 비밀번호 보관, 토큰 회전, 로그인 방어와 계정 복구 책임이 제품 범위를 넘어선다.

현재 운영 배포 공급자와 실제 관리자 계정은 정해지지 않았지만, 검수 화면과 승인 유스케이스가 사용할 인증 계약은 먼저 고정해야 한다.

## 결정

관리자 신원 확인과 세션 관리는 Clerk Next.js SDK를 사용한다.

- 공개 디렉터리는 로그인 없이 계속 이용한다.
- `clerkMiddleware()`는 Next.js 요청에서 인증 상태를 사용할 수 있게만 구성한다.
- 관리자 페이지, 데이터 조회와 모든 Server Action은 각 리소스 가까이에서 인증과 권한을 다시 확인한다.
- 자체 비밀번호, 세션 토큰 또는 JWT를 저장하거나 발급하지 않는다.
- MVP 역할은 `reviewer`와 `admin`으로 구분한다.
- 역할 부여는 서버 전용 환경변수의 Clerk 사용자 ID allowlist로 시작한다.
  - `CLERK_REVIEWER_USER_IDS`
  - `CLERK_ADMIN_USER_IDS`
- `admin`은 `reviewer` 권한을 포함한다.
- 감사 이력의 `actor_id`에는 Clerk 사용자 ID를 저장하며 이메일이나 이름을 복제하지 않는다.
- 로그인 UI는 가입을 제공하지 않고, 운영자가 Clerk에서 미리 허용한 계정만 사용한다.

실제 키와 사용자 ID는 환경별 비밀·설정으로 관리하며 Git에 기록하지 않는다. 운영 Clerk 프로젝트 생성, 허용 로그인 방식, MFA와 계정 초대 정책은 배포 준비 작업에서 확정한다.

## 결과

장점:

- 비밀번호와 세션 보안 구현을 관리형 공급자에 맡긴다.
- Next.js Server Component, Route Handler와 Server Action에서 같은 신원 계약을 사용한다.
- 감사 로그는 안정적인 외부 사용자 ID로 처리자를 추적한다.
- 작은 초기 운영팀은 별도 사용자·역할 테이블 없이 시작할 수 있다.

단점:

- 관리자 기능이 Clerk 가용성과 설정에 의존한다.
- 역할 변경에 환경설정 갱신과 재배포가 필요하다.
- 공급자 이전 시 세션과 사용자 식별자 매핑 작업이 필요하다.
- 실제 로그인 통합 검증은 Clerk 개발·운영 키가 준비되어야 가능하다.

## 대안

- 자체 이메일/비밀번호와 세션: 외부 의존성은 줄지만 보안·복구·오남용 방어 책임이 과도하다.
- Auth0: 성숙한 엔터프라이즈 기능이 강점이지만 현재 소규모 관리자 MVP에는 설정 복잡도가 더 크다.
- Descope: 비밀번호 없는 흐름과 시각적 구성은 유용하지만 현재 요구에는 Clerk의 Next.js 통합과 사전 구성 UI가 더 단순하다.
- Clerk 조직 역할: 역할 운영은 편리하지만 초기 allowlist보다 설정 범위가 크므로 운영 인원이 늘 때 검토한다.

## 재검토 조건

관리자 수가 늘어 역할 변경이 자주 발생하거나, 조직별 권한·승인 분리·SSO·감사 내보내기가 필요하거나, 공급자 비용·가용성·규제 요구가 현재 선택과 맞지 않을 때 Clerk 조직 역할, 애플리케이션 역할 테이블 또는 다른 관리형 인증 공급자를 비교한다.
