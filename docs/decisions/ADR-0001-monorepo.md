# ADR-0001: 단일 저장소(monorepo) 사용

- 상태: 승인
- 결정일: 2026-07-22

## 맥락

초기 제품은 Next.js 웹, Python 수집기, 데이터·운영 문서와 인프라 설정이 함께 변한다. 팀과 서비스 규모가 작고, 공개 데이터 계약과 검수 정책의 일관성이 독립 저장소 운영보다 중요하다.

## 결정

웹, 수집기, 문서, 인프라와 보조 스크립트를 하나의 Git 저장소에서 관리한다.

- `apps/web`: Next.js 애플리케이션
- `services/collector`: Python 수집기
- `docs`: 제품·설계·운영·ADR
- `infra`: 인프라 설정
- `scripts`: 공통 보조 도구

각 애플리케이션은 자체 의존성·잠금 파일과 실행 명령을 유지한다. 루트 문서가 공통 계약과 작업 순서를 정의한다. 초기에는 별도 monorepo 빌드 도구를 필수로 도입하지 않는다.

## 결과

장점:

- 관련 코드와 데이터 계약을 한 변경에서 검토할 수 있다.
- 문서와 구현의 버전을 맞추기 쉽다.
- 초기 개발 환경과 협업 절차가 단순하다.

단점:

- 언어별 도구와 생성물을 하나의 저장소에서 관리해야 한다.
- 저장소가 커지면 CI 범위와 소유권 경계가 복잡해질 수 있다.
- 독립 배포 단위가 Git 저장소 경계로 강제되지 않는다.

## 대안

- 웹과 수집기별 저장소: 독립성은 높지만 초기 계약 변경과 문서 동기화 비용이 크다.
- 웹 안에서 JavaScript로 수집기 구현: 도구 수는 줄지만 Python 생태계와 독립 작업 실행의 장점을 포기한다.

## 재검토 조건

접근 권한을 저장소 수준으로 분리해야 하거나, CI 시간이 과도해지거나, 팀별 독립 릴리스가 상시 충돌할 때 재검토한다.
